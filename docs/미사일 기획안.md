# Missile 객체 구조 설계 검토

## 1. 결론

현재 구조에는 **`Simulation`이 월드 정보를 소유하고, `Missile`은 자기 상태와 생명주기를 소유하는 하이브리드 방식**이 가장 잘 맞는다.

- `Simulation`은 이미 `spaceSize_`, `rocket_`, `randomness`, `dt`를 알고 있다.
- `Missile`은 `Transform`, `RigidBody`, 활성/대기 상태, 남은 부활 시간, 난수 생성기를 소유한다.
- 매 프레임 `Simulation`이 소유권 없는 값만 `Missile::update`에 전달한다.
- `Missile`은 화면 밖 판정, 사망, 부활 대기, 재등장을 스스로 처리한다.
- 미사일은 로켓 객체 전체를 알 필요가 없다. 재등장 순간의 `rocket.transform().center()` 값만 받으면 된다.

권장 호출 형태는 다음 둘 중 하나다.

```cpp
missile_.update(constants_.dt, spaceSize_, rocket_.transform().center());
```

인자가 늘어날 가능성이 있다면 작은 문맥 객체가 더 낫다.

```cpp
struct MissileWorldView {
    Size bounds;
    Vec2 targetCenter;
};

missile_.update(constants_.dt, {
    .bounds = spaceSize_,
    .targetCenter = rocket_.transform().center(),
});
```

이 방식은 `Missile`이 행동을 주도한다는 현재 의도를 유지하면서도 `Rocket&`나 `Simulation&`를 필드로 저장하지 않는다.

## 2. 현재 코드에서 실제로 필요한 정보

현재 `missile.hpp`의 동작을 기준으로 의존성을 나누면 다음과 같다.

| 정보 | 필요한 시점 | 권장 소유자 | 전달 방법 |
|---|---|---|---|
| `Transform`, `RigidBody` | 항상 | `Missile` | 필드 |
| 활성/부활 대기 상태 | 항상 | `Missile` | 필드 |
| 남은 부활 시간 | 대기 중 | `Missile` | 필드 |
| 난수 상태 | reset 및 부활 시 | `Missile` 또는 `Simulation` | 필드 또는 인자 |
| 화면 크기 | 생성 위치 및 이탈 판정 시 | `Simulation` | 값/읽기 전용 문맥 인자 |
| 로켓 중심점 | 미사일 생성 시 | `Simulation` | `Vec2` 값 인자 |
| 미사일 랜덤 설정 | reset 및 부활 시 | `Simulation` 또는 불변 설정 객체 | 생성자/인자 |

중요한 점은 미사일이 현재 **유도탄처럼 매 프레임 로켓을 추적하는 것이 아니라**, 재등장할 때 로켓 근처를 조준한 초기 속도를 얻는다는 것이다. 따라서 `Rocket` 객체의 참조를 계속 보관할 이유가 없다. 조준 시점의 `Vec2 targetCenter` 스냅샷이면 충분하다.

## 3. 권장안: 값 문맥을 받는 자율 상태 머신

### 3.1 책임 분리

`Simulation`의 책임:

- 월드 크기와 로켓 소유
- 프레임 순서 결정
- reset seed에서 각 객체용 난수 스트림 구성
- `MissileWorldView` 생성 및 전달

`Missile`의 책임:

- 비행 물리 업데이트
- 화면 밖 이탈 판정
- 활성 상태에서 대기 상태로 전환
- 무작위 부활 시간 선택
- 대기 시간 감소
- 시간이 끝나면 주어진 화면 크기와 타겟 위치를 이용해 재등장

### 3.2 상태 표현

현재의 `bool live_`와 `reviveSchedule_ == -1/0/>0` 조합은 유효하지 않은 조합을 만들 수 있다. 예를 들어 `live_ == true`인데 부활 카운터가 양수인 상태도 표현된다. 상태를 명시하는 편이 안전하다.

```cpp
enum class MissileState {
    Active,
    WaitingForRespawn,
};
```

필요해질 때만 `Disabled`를 추가한다. 지금 요구사항에는 두 상태로 충분하다.

```text
Simulation::reset
       │
       ▼
    Active ── 화면 밖 ──> WaitingForRespawn
       ▲                         │
       └──── 대기 시간 만료 ─────┘
```

### 3.3 예상 인터페이스

아래는 방향을 보여 주는 API 스케치이며 곧바로 복사할 완성 구현은 아니다.

```cpp
struct MissileWorldView {
    Size bounds;
    Vec2 targetCenter;
};

class Missile {
public:
    void reset(
        const MissileWorldView& world,
        const constants::Randomness::Missile& config,
        std::optional<unsigned int> seed = std::nullopt
    );

    void update(
        float dt,
        const MissileWorldView& world,
        const constants::Randomness::Missile& config
    );

    [[nodiscard]] bool active() const;

private:
    void spawn(const MissileWorldView& world,
               const constants::Randomness::Missile& config);
    void beginRespawnWait(const constants::Randomness::Missile& config);
    [[nodiscard]] bool isOutside(Size bounds) const;
};
```

내부 업데이트 순서는 다음처럼 정할 수 있다.

```cpp
if (state_ == MissileState::WaitingForRespawn) {
    respawnRemaining_ -= dt;
    if (respawnRemaining_ <= 0.0f) {
        spawn(world, config);
    }
    return;
}

rb_.update(dt);
transform_.move(rb_.linearVel() * dt);
transform_.rotate(rb_.angularVel() * dt);

if (isOutside(world.bounds)) {
    beginRespawnWait(config);
}
```

`spawn`은 그 호출 순간 전달된 `targetCenter`를 사용하므로, 첫 reset과 이후 부활 모두 당시 로켓 위치를 향하게 된다. 비행 중에는 타겟을 다시 읽지 않는다.

### 3.4 장단점

장점:

- `Missile`이 원하는 자율적인 생명주기를 유지한다.
- `Rocket`과 `Simulation`에 대한 직접 결합이 없다.
- 포인터 수명, null 여부, 복사 후 참조 꼬임을 걱정할 필요가 없다.
- 테스트에서 임의의 화면과 타겟 좌표를 간단히 주입할 수 있다.
- 추후 타겟이 로켓이 아닌 다른 객체가 되어도 `Vec2`만 전달하면 된다.

단점:

- `update` 호출부에 문맥 전달 코드가 생긴다.
- 객체가 많아지고 공통 문맥이 커지면 별도 시스템 설계가 더 적합해질 수 있다.

## 4. 대안 1: 필요한 값을 매개변수로 직접 전달

문맥 구조체 없이 가장 단순하게 시작하는 방식이다.

```cpp
void Missile::update(
    float dt,
    Size spaceSize,
    Vec2 targetCenter,
    const constants::Randomness::Missile& config
);
```

장점:

- 의존성이 함수 시그니처에 그대로 드러난다.
- 별도 타입이 없어 현재 규모에서 가장 간단하다.
- 모든 값이 작고 소유권 문제가 없다.

단점:

- 인자가 더 늘면 시그니처가 지저분해진다.
- 여러 미사일 관련 함수에서 같은 인자 묶음을 반복할 수 있다.

현재 기능만 구현하고 확장 계획이 크지 않다면 이 방법도 충분하다. 인자가 세 개 이상 반복되기 시작할 때 `MissileWorldView`로 묶으면 된다.

## 5. 대안 2: `Simulation`이 생명주기 전체를 관리

`Missile`을 물리 데이터와 기본 동작만 가진 수동 객체로 만들고, 화면 이탈과 부활은 `Simulation::update`에서 처리한다.

```cpp
missile_.update(constants_.dt);

if (isOutside(missile_.transform(), spaceSize_)) {
    missile_.deactivate();
    missileRespawnTimer_ = sampleRespawnDelay();
}

if (!missile_.active() && missileRespawnTimer_ <= 0.0f) {
    missile_.spawn(spaceSize_, rocket_.transform().center(), randomness.missile);
}
```

장점:

- 월드 규칙이 `Simulation` 한곳에 모인다.
- `Missile`은 월드 크기나 로켓을 전혀 모른다.
- 객체 간 충돌, 보상, 난이도 조절처럼 전역 규칙과 연결하기 쉽다.

단점:

- 미사일의 한 생명주기가 `Simulation`과 `Missile`에 나뉜다.
- 미사일 수가 늘면 `Simulation`이 빠르게 비대해진다.
- 사용자가 원하는 “혼자 알아서 죽고 부활하는 객체”와는 거리가 있다.

화면 이탈이 단순한 미사일 내부 규칙이 아니라 게임 전체의 이벤트로 취급되어야 한다면 적합하다. 현재 단계에서는 권장안보다 얻는 이점이 작다.

## 6. 대안 3: `MissileSystem` 또는 `MissileSpawner` 분리

미사일 엔티티와 생명주기 관리자를 나눈다.

```cpp
class MissileSystem {
public:
    void reset(Size bounds, Vec2 targetCenter, unsigned int seed);
    void update(float dt, Size bounds, Vec2 targetCenter);

private:
    Missile missile_;
    MissileState state_;
    float respawnRemaining_;
    std::mt19937 rng_;
};
```

또는 여러 미사일을 다룬다면 `std::vector<Missile>`과 각 개체의 타이머를 관리할 수 있다.

장점:

- `Missile`은 순수한 엔티티로 남는다.
- 여러 발, 오브젝트 풀, 최대 동시 발사 수, 웨이브 같은 확장에 유리하다.
- `Simulation`이 세부 생명주기로 비대해지는 것을 막는다.

단점:

- 현재 미사일 한 발에는 계층이 과하다.
- `Missile`과 `MissileSystem` 중 어느 쪽이 상태를 가져야 하는지 규칙을 잘 정해야 한다.

가까운 시일 내에 미사일이 여러 발로 늘어나거나 스폰 정책이 복잡해질 예정이라면 가장 장기적인 구조다. 그렇지 않다면 권장안으로 시작한 뒤 필요할 때 상태와 RNG를 `MissileSystem`으로 옮겨도 늦지 않다.

## 7. 대안 4: `Rocket`과 화면의 참조를 필드로 보관

```cpp
class Missile {
    const Rocket& target_;
    const Size& bounds_;
};
```

또는 포인터를 사용할 수 있다.

```cpp
const Rocket* target_;
const Size* bounds_;
```

장점:

- `update(dt)`만 호출할 수 있어 겉보기에는 편하다.
- 유도탄처럼 매 프레임 타겟의 최신 상태를 읽어야 할 때 직접적이다.

단점:

- `Missile`의 수명이 참조 대상보다 짧아야 한다.
- 현재 `Simulation`은 렌더링 큐에서 값으로 복사된다. 기본 복사를 허용한 채 내부 참조/포인터를 두면 복사된 미사일이 원본 `Simulation`의 로켓을 가리키는 문제가 생길 수 있다.
- 초기화 순서와 복사/이동 생성자 정책이 까다로워진다.
- `Missile` 단위 테스트에 실제 `Rocket`이 필요해진다.
- 현재는 부활 순간의 좌표만 필요하므로 과한 의존성이다.

따라서 현재 코드에는 권장하지 않는다. 나중에 실제 유도 로직이 필요해져도 `Rocket&` 전체보다 `TargetView`나 현재 위치 값을 매 프레임 전달하는 편이 보통 더 안전하다.

## 8. 대안 5: 콜백으로 월드 정보 조회

```cpp
using TargetProvider = std::function<Vec2()>;
using BoundsProvider = std::function<Size()>;
```

`Missile`이 이 콜백들을 보관하고 필요할 때 호출하게 할 수 있다.

장점:

- 구체적인 `Rocket` 타입과 결합되지 않는다.
- 타겟 선택 정책을 실행 중 바꾸기 쉽다.

단점:

- 콜백이 캡처한 객체의 수명 문제가 여전히 존재한다.
- 실제 의존성과 실행 비용이 함수 시그니처 뒤로 숨는다.
- 복사되는 `Simulation`에서 캡처가 원본 객체를 가리킬 위험이 있다.
- 현재 요구사항에는 복잡도만 늘어난다.

타겟 선택이 매우 동적이고 다양한 정책 객체를 플러그인처럼 교체해야 할 때 고려할 수 있지만, 지금은 값 전달이 더 명료하다.

## 9. 세부 구현 결정에서 주의할 점

### 9.1 부활 시간은 초와 step 중 하나로 명시한다

현재 `minRevivePeriod = 120`, `maxRevivePeriod = 480`과 `int reviveSchedule_`은 step 단위처럼 보이지만, `dt`가 바뀌면 실제 시간이 달라진다.

권장 방식은 초 단위다.

```cpp
float minRespawnDelaySeconds;
float maxRespawnDelaySeconds;
float respawnRemainingSeconds_;
```

매 프레임 `respawnRemainingSeconds_ -= dt`로 처리하면 시뮬레이션 주파수와 독립적이다. 의도적으로 step 단위를 쓴다면 이름을 `minRespawnDelaySteps`, `respawnStepsRemaining_`처럼 명시하고 정수 타입을 사용한다.

### 9.2 비활성 상태에서는 물리를 업데이트하지 않는다

현재 `update`는 `live_` 검사 전에 `RigidBody`와 `Transform`을 갱신한다. 대기 중 미사일도 계속 이동할 수 있으므로 상태를 먼저 분기하는 편이 안전하다.

### 9.3 화면 밖 판정 기준을 통일한다

로켓 종료 판정과 같은 규칙이라면 미사일도 다음 조건을 사용할 수 있다.

```cpp
tf.right() < 0 ||
tf.left() > static_cast<float>(bounds.width) ||
tf.top() < 0 ||
tf.bottom() > static_cast<float>(bounds.height)
```

이는 미사일의 일부만 화면 밖에 나간 순간이 아니라 **전체가 화면 밖으로 빠진 순간** 사망시킨다. 중심점이 경계를 넘는 즉시 죽이는 규칙을 원한다면 별도로 이름을 붙여 차이를 명확히 해야 한다.

### 9.4 `reset`과 `spawn`의 의미를 분리한다

- `reset`: 에피소드 전체 초기화, RNG 재설정, 첫 미사일 즉시 생성
- `spawn`: 현재 RNG를 사용해 한 번 등장
- `beginRespawnWait`: 사망 처리 및 다음 대기 시간 샘플링

이렇게 나누면 에피소드 reset과 반복 부활이 뒤섞이지 않는다.

### 9.5 난수 생성기는 매 부활마다 새로 만들지 않는 편이 낫다

현재처럼 호출마다 `std::mt19937`를 새 seed로 생성할 수도 있지만, 일반적으로 객체마다 RNG를 하나 유지하면 시퀀스와 상태가 더 명확하다.

```cpp
std::mt19937 rng_;
```

`reset(seed)`에서 한 번 seed를 설정하고, 이후 spawn과 대기 시간 샘플링이 같은 스트림을 순서대로 소비하게 한다. 재현 가능한 학습 환경이라면 `Simulation`의 하나의 seed로부터 로켓용 seed와 미사일용 seed를 분리해야 한다. 같은 seed로 각각 동일한 RNG를 시작하면 서로 다른 객체의 난수에 원치 않는 상관관계가 생길 수 있다.

### 9.6 설정은 가능하면 불변 참조로 받는다

`constants::Randomness::Missile`은 작은 타입이라 값 복사도 문제는 없지만 설정이라는 의미를 드러내려면 `const ...&`가 적합하다. 설정이 런타임에 바뀌지 않는다면 생성 시 `MissileConfig`로 보관하는 설계도 가능하다. 다만 현재 `Simulation`이 `randomness`를 모아 관리하므로 우선은 인자 전달이 일관적이다.

### 9.7 이름과 불변식을 정리한다

- `revievSchedule`은 `scheduleRespawn` 또는 `beginRespawnWait`로 수정 대상이다.
- `live_`보다 `state_` 또는 최소한 `active_`가 `activated()`와 의미가 맞는다.
- `reviveSchedule_`의 `-1` 같은 sentinel 대신 명시적 상태를 사용한다.
- spawn 완료 시 활성 상태 전환을 한곳에서 수행한다.
- 사망 처리 시 속도 초기화 여부를 한곳에서 결정한다.

## 10. reset부터 반복 부활까지의 권장 흐름

1. `Simulation::reset(seed)`가 로켓을 먼저 reset한다.
2. 로켓 reset 후의 중심점과 `spaceSize_`로 `MissileWorldView`를 만든다.
3. `missile_.reset(world, randomness.missile, missileSeed)`를 호출한다.
4. 미사일은 RNG를 초기화하고 화면 좌우 중 한 곳에서 즉시 spawn한다.
5. spawn 순간 로켓 중심 근처에 오차를 더한 지점을 향하도록 초기 속도를 한 번 계산한다.
6. 활성 상태에서는 매 프레임 탄도 운동만 수행한다.
7. 미사일 전체가 화면 밖으로 나가면 `WaitingForRespawn`으로 바꾸고 무작위 대기 시간을 뽑는다.
8. 대기 중에는 물리를 갱신하지 않고 남은 시간만 감소시킨다.
9. 시간이 끝나면 그 순간 전달된 최신 로켓 중심점을 이용해 다시 spawn한다.
10. 이후 6~9를 반복한다.

프레임에서 로켓과 미사일 중 무엇을 먼저 업데이트할지도 고정해야 한다. `rocket_.update(...)` 후 `missile_.update(...)`를 호출하면 미사일 부활은 해당 프레임의 최신 로켓 위치를 조준한다. 반대 순서면 이전 프레임 위치를 사용한다. 차이는 작지만 재현성을 위해 순서를 명시하는 편이 좋다.

## 11. 선택 기준 요약

| 방안 | 결합도 | 현재 구현량 | 복사 안전성 | 다수 미사일 확장 | 현재 추천도 |
|---|---:|---:|---:|---:|---:|
| 값/문맥 인자 + `Missile` 상태 머신 | 낮음 | 낮음 | 높음 | 보통 | 가장 추천 |
| 직접 인자 전달 | 낮음 | 가장 낮음 | 높음 | 보통 | 작은 규모에 추천 |
| `Simulation`이 전체 관리 | 낮음 | 보통 | 높음 | 낮음 | 전역 규칙 중심일 때 |
| `MissileSystem` 분리 | 낮음 | 높음 | 높음 | 높음 | 여러 발 계획 시 |
| 참조/포인터 필드 | 높음 | 겉보기엔 낮음 | 낮음 | 낮음 | 비추천 |
| 콜백 provider | 보통 | 높음 | 주의 필요 | 보통 | 동적 정책이 필요할 때 |

## 12. 최종 제안

지금은 다음 경계가 가장 단순하고 확장 가능하다.

```text
Simulation
  ├─ Rocket, Missile, spaceSize, dt, randomness 소유
  ├─ Rocket을 먼저 업데이트
  └─ Size와 targetCenter 값을 Missile::update에 전달

Missile
  ├─ Transform, RigidBody, RNG 소유
  ├─ Active / WaitingForRespawn 상태 소유
  ├─ 화면 이탈을 스스로 판정
  └─ 사망 → 대기 → spawn 생명주기를 스스로 수행
```

즉, **행동은 `Missile`이 결정하되, 월드 객체를 소유하거나 참조하지 않고 `Simulation`이 제공하는 작은 읽기 전용 스냅샷만 사용한다.** 향후 미사일이 여러 발로 늘어나는 시점에 이 상태 머신과 RNG 관리 책임을 `MissileSystem`으로 옮기는 것이 자연스러운 다음 단계다.
